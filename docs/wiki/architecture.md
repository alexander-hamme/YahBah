# Architecture Overview

YahBah takes a job URL and autonomously fills and submits the application, using local Ollama models, a headless Chrome driven by browser-use (headed for a run whose page walls off the headless one, see below), and Temporal for durable orchestration. Everything is async (asyncio, psycopg3 via SQLAlchemy `postgresql+psycopg`, httpx).

## Processes
- **API**: FastAPI app `yahbah.api.main:app` (`src/yahbah/api/`). Enqueues Temporal workflows, serves run/application data. See [api-frontend](modules/api-frontend.md).
- **Worker**: `python -m yahbah.worker` (`src/yahbah/worker.py`). Runs the `ApplicationWorkflow` + activities and two background Gmail pollers. See [workflows](modules/workflows.md), [gmail](modules/gmail.md).
- **Frontend**: Next.js app in `frontend/`.
- **External**: Postgres, Temporal server, Ollama, Gmail API.

## Run flow
`POST /jobs` -> workflow `ApplicationWorkflow` (`src/yahbah/workflows/application.py`):
QUEUED (wait for run slot) -> DISCOVER -> MAP_FORM -> EXTRACT_METADATA -> CHECK_DUPLICATE -> MAP_ANSWERS -> GENERATE_COVER_LETTER (only if the form asks for one) -> FILL, then by the run's `submission_mode`, snapshotted when it is created from the runtime setting:
- `testing`: ends `COMPLETED` after FILL; nothing is submitted.
- `review` (the default, and what a missing or invalid setting means): the filled form's evidence is saved, the browser closes and the run waits as `AWAITING_REVIEW` (default 48 h). An approval queues for a run slot, re-fills exactly the approved answers and runs SUBMIT -> DONE. A required field nobody approved sends the run back to review; a rejection or an expired window submits nothing.

DISCOVER ends a run early when code finds a dead end: `blocked` (a bot wall), `job_closed`, `captcha`, `login_wall` or `browser_error`, judged from page evidence (see the design rule below). Browser stages call `yahbah.agent`; LLM stages call `yahbah.llm`. Statuses, reasons, the dedup predicate and the submission claim are in the [run-lifecycle contract](contracts/run-lifecycle.md).

**MAP_ANSWERS (and the answers to fields that appear while filling) is the two-pass grounded answer engine** (`llm/answers.py`, [llm](modules/llm.md)): form schema plus job context → Pass 1 interprets every field and selects fact ids → code retrieves the full fact blocks → Pass 2 composes the final value and cites fact ids → deterministic checks (`llm/answer_checks.py`) → an independent verifier → at most one recovery round → a `FieldMapping` plan that the deterministic fill executes. The applicant's knowledge is a typed `facts:` list in the gitignored `config/personal.yaml` plus facts built from the profile (`llm/facts.py`). A required question the facts can't support fails closed: the run ends `FAILED` / `needs_answer` and its page lists each question with the information needed and a paste-ready fact skeleton; an optional one is left blank. The user edits `personal.yaml` and retries (no write API).

## Core design rule: code first, models as fallbacks
Each browser stage tries deterministic code, then one structured model call, then an agent loop; each tier's output is verified in code before acceptance. No agent ever has a submit tool; submit is gated code (`agent/submit.py`), and structural page evidence, not a model, decides that it worked. Agents do have generic click and key actions, so every agent phase runs through `GuardedTools`, which refuses actions on submit or advance controls (one classifier, `agent/controls.py`); a post-agent tripwire records a possible submission if the page still changed. The same rule holds for answers: **models propose, code decides what is written.** The fill executors write only planned values; the fix agent's `fill_field` writes only a field's planned value and its free-text `input` only text contained in a planned answer; a planned value that matches no option of the live widget is re-answered once through the engine, never chosen by an agent. Details: [agent](modules/agent.md).

**Discover's dead ends are classified by code, not by models or page text.** `discover.classify_page` reads evidence (the main document's HTTP status, vendor bot-wall markup, the board's closure URL, visible controls) and a model's "job closed / login / captcha" is only advice in the failure detail; precedence is [contract §2](contracts/run-lifecycle.md). A wrapper page that names a board's job is first swapped for the board's own form, verified in the browser (no side-channel HTTP). If the page still blocks the headless browser, discover reopens it once in a fresh, throwaway, headed Chromium (setting `browser_headed_fallback`, default on) and the run stays headed; otherwise the run ends `blocked`.

**Never evade.** YahBah adds no stealth or fingerprint masking of its own (browser-use's default launch flags are accepted as they are), and uses no captcha solving, proxies or retry loops against a protection. A protected page is reached by a legitimate route or the run ends `blocked`.

**Answers rest on facts, and fail closed.** Every non-generated answer cites fact ids (`basis`); open-ended prose is `generated`, may only rephrase cited facts and add none, and is shown in review. Nothing the models say is trusted as is: field and fact ids are schema enums, code re-derives what it can (option membership, formats, dates, numbers, citations), and a separate verifier call reads each answer against its cited facts. A job description is untrusted context, never evidence: the verifier never sees it, only the job's location and (since 2026-11-09) a small set of quoted claims about what the job offers (contract C9), labelled untrusted, usable only for the job side of an answer, and still page-derived ([llm](modules/llm.md#job-offers-and-the-verifiers-claims-section-contract-c9-2026-11-09)). The `answer_plan` artifact records every plan with fact ids only, never fact values.

## Other invariants (verified in source)
- Page content/personal data stay local: telemetry, cloud sync and browser-use's PyPI version check (`BROWSER_USE_VERSION_CHECK=false`, which otherwise queries PyPI at every Agent start) are disabled in `src/yahbah/agent/__init__.py` (must be imported before `browser_use`).
- One browser session per run (`SessionRegistry`), in-process only, so it is lost when the worker stops. The session is headless unless discover moved the run to the headed fallback; that is carried in workflow state (`DiscoverOutput.headed`) so a re-opened browser in a later stage, or after a restart, is headed too and never falls back on its own. **Restart policy is resume:** the worker writes no run status when it starts or stops. The Temporal workflow stays alive and, when a worker is next available, retries the interrupted activity (within its 2-attempt retry policy); activities re-open the job URL and re-check the form. A run that had already claimed its submission only verifies, or ends `SUBMIT_UNCERTAIN`. Stale attempts are fenced out by a DB-level attempt lease. Details in [workflows](modules/workflows.md) and [contract §7](contracts/run-lifecycle.md).
- **Nothing is submitted without a code-recorded claim.** `run_state.claim_submission()` atomically sets `submit_attempted_at` and inserts a `submission_claim` row (one per posting, outliving its run) after the submit button is located and before the first click; no claim, no click. A retry after that only verifies, and re-clicks only on code-detected validation errors or code inputs. A run that attempted and has no code-verified success ends `SUBMIT_UNCERTAIN`, is never retried automatically, and blocks new applications to the posting (`possibly_applied()`) until the user resolves it ([contract §5, §6](contracts/run-lifecycle.md)).
- Each application uses a per-run email alias (`user+xxxx@...`, `src/yahbah/credentials.py`) so replies can be matched back.
