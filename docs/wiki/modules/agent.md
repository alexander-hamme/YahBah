# Agent / Browser Automation (`src/yahbah/agent/`)

Replaces the deleted `browser/` package. The module docstring in `agent/__init__.py` has the full tier table; read it first. Uses `browser-use==0.13.11` (pinned in `pyproject.toml`) over local Ollama.

## Stages and tiers
| Stage | File | Tiers (code -> one-shot model -> agent) |
|---|---|---|
| discover (reach form) | `discover.py` | dead-end check in code, board route, `read_form_schema` / click "Apply" -> element-pick call -> navigation agent; see [Discover](#discover) |
| map_form | `discover.py` | `read_form_schema` -> cleaned-HTML-to-fields call (selectors verified on page) -> mapping agent |
| job info | `discover.py` | schema.org JSON-LD -> metadata model on page text |
| fill | `fill.py` | per-type executors (text, select, combobox, radio/checkbox, file via CDP), read-back diff + one retry -> option-miss replan (once, first fill only) -> fix agent (guarded, no submit; see [Submit boundary](#submit-boundary)) |
| submit/verify | `submit.py` | gate in code, locate, claim, click, then a verify loop decided by structural page evidence (`settings.submit_max_attempts` rounds); the model only advises |

Failures raise `StageFailed` (discover.py) with reasons such as `fill_failed`, `needs_answer`, `submit_button_not_found`, `claim_denied`, `submit_unverified`, `possibly_submitted`, `captcha`, `login_wall`, `job_closed`, `blocked` (the set is `FailureReason` in `run_state.py`). At discover, `blocked`, `job_closed`, `captcha`, `login_wall` and `browser_error` come only from code evidence ([Discover](#discover)); the submit stage's model advice can still name a blocker (below). `discover.map_form(force_tier="schema"|"oneshot"|"agent")` can start at a lower tier (used by `scripts/run_pipeline.py --force-tier`).

## Support files
- `controls.py`: the submit/advance control classifier (one JS definition), the submit locator, the agent guard (`GuardedTools`) and the fix-agent tripwire. See [Submit boundary](#submit-boundary).
- `tools.py`: our named browser-use tools (`read_form_schema`, dropdown readers, `look_at_screen`, gated `inspect_page_js` locked until a stall; deny-list is a guard rail, not a sandbox), `StallTracker`, `run_js`. Fields are addressed by an invisible `data-ja-field` key stamped on each element. `READ_FORM_SCHEMA_JS` also reads, per field, `description` (the text of its `aria-describedby` ids, ≤300 chars; for a group the fieldset's, else the first member's) and `section` (the nearest visible heading above it: `h1`-`h4`, `[role=heading]` or an enclosing fieldset's legend that is not the field's own label, ≤120 chars). Both are left out when empty and flow into `FormField.description` / `.section` for the answer engine ([llm](llm.md)). Option lists are shown up to **40** (native select, open and own-option readers; `options_total` says when there are more); the agent-tier prompts still say "at most 15" as their own fallback.
- `llm.py`: `chat_model(role)` (a `LoggingChatOllama` that logs raw replies), `Crew` (driver/vision/escalation), `Escalator` (hands steps to the escalation model on stall), `run_agent(task, crew, session, max_steps, output, *, mode="form")` (agent tuned for slow local models; **every** agent phase goes through it, and `make_tools` only builds `GuardedTools`, so every phase is guarded). The step limit is passed by each caller and hard-coded there: navigation 6, dropdown reader 4, mapping agent 15 (`discover.py`), fill-fix agent 10 (`fill.py`). `settings.agent_max_steps` exists but is never read.
- `boards.py`: `BoardProfile` per job board (URL patterns, DOM signature, iframe embed patterns, stage hooks, `model_notes`, `submit_button_js` (a hook returning the control's text or null, tagging it `submit-cta`; no board sets it), the board-route hooks (`application_routes`, `route_verified`, `job_id_in_url`, `closed_url_patterns`; see [Discover](#discover)), and the verification-code email shape: `email_code_subject` as the Gmail subject filter and `email_code_pattern`, a regex the whole code must match, which Greenhouse sets to `[A-Za-z0-9]{8}`; `submit.py` passes both to `GmailClient.wait_for_verification_code`, see [gmail](gmail.md)). Registered: `GREENHOUSE`, `GENERIC` fallback. `detect_board`, `embedded_form_url`, `board_routes`, `board_id_in_url`, `record_blocked`, `with_notes`. Workday and Lever URLs are recognised elsewhere (Workday in `credentials.py` alias hashing and `gmail/alert_parser.py`; Lever in `alert_parser.py` and the company-domain heuristic in `workflows/activities/db_ops.py`) but have no `BoardProfile`, so they run as `generic`. `record_observation` appends (board, which tier succeeded at each stage, field count) to `artifacts/_observations.jsonl`, but only from `map_form_activity` after `map_form` succeeds and from `scripts/run_pipeline.py` when its run completes without raising. Failed runs, and runs that never reach `map_form`, leave no observation. (The `boards.py` module docstring says "every run"; that is inaccurate.) `record_blocked` appends one `event: "blocked"` row (url, board, signal, `board_id_in_url`) to the same file for every `blocked` discover.
- `session.py`: `SessionRegistry` (singleton, `run_id` -> `BrowserSession`, own temp Chrome profile each; `open(run_id, url, *, headed=False)`, `reopen_headed(session, url)`) and `artifact_path(run_id, filename)`. A headed session is a visible Chrome window with a fresh `tempfile.mkdtemp` profile (prefix `HEADED_PROFILE_PREFIX`), deleted when the session closes or is replaced; launch flags are browser-use's defaults, with no masking of ours. `reopen_headed` starts the headed browser first, so if it can't launch the run keeps its headless one and the error propagates; it checks ownership before and after the (slow) launch and raises `SessionSuperseded` if the run changed hands.

## Discover
Contract [run-lifecycle](../contracts/run-lifecycle.md) §2 is authoritative for the reasons, their precedence, the board-route and headed-fallback rules and the retryability; this section is where the code lives (`discover.py`, `boards.py`, `session.py`).

**Order in `discover(session, trace, *, headed_fallback=False)`:**
1. Job info is read first, unless the page already has any verdict (a block page holds none; it is then read from wherever the form turns up); an embedded board form is followed.
2. **Board route** (below), when the page names a board job.
3. **Dead-end check** (`dead_end_verdict`): `blocked`, `job_closed` and `browser_error` end discover here with no model call.
4. **Headed fallback**, only for a `blocked` verdict and only if `headed_fallback`: `_headed_fallback` calls `reopen_headed` once and re-checks the page. If the headed page is also walled the run ends `blocked` with `headed: blocked`; if it shows another dead end, that reason with `headed: yes`; if no headed browser can be had, `blocked` with `headed: unavailable` (the headless one is kept). Otherwise the run continues headed and every later failure detail says `headed: yes`. `DiscoverResult.headed` reports it.
5. The existing tiers: form already on page, click "Apply", one-shot element pick, navigation agent. The dead-end check runs again after a click that led nowhere and after each one-shot click that showed no form.
6. If no form was reached, the check runs once more with `late=True`, which also allows `captcha` and `login_wall` (a guest-apply path may exist); only then `form_not_found`, with the agent's answer quoted as `model advice`.

**`classify_page(PageEvidence, board) -> PageVerdict | None`** is pure (no session, no model, no page words as evidence). `PageEvidence` is read by `read_page_evidence` from one JS call: the main document's HTTP status (Navigation Timing, `None` when unknown), title, text, HTML (heads only), visible controls, visible captcha widgets (`CAPTCHA_WIDGETS`, not the invisible reCAPTCHA v3 badge) and visible password fields. Evidence is code only: `BLOCK_SIGNATURES` (Akamai, Cloudflare, PerimeterX, DataDome, Imperva, each anchored in markup), `BLOCK_STATUSES` (401/403/407/429) and `GONE_STATUSES` (404/410) on an inert page (`INERT_MAX_CONTROLS` = 5 or fewer visible controls), the board's `closed_at(url)`, and widgets or password fields. A visible application form beats any verdict (`dead_end_verdict` checks `looks_like_form`), and a status-only verdict must keep holding for `STATUS_RECHECK_SECS` (a slow app renders late). `dead_end()` builds the `StageFailed`; its detail carries the signal, HTTP status and URL. `LATE_REASONS` = `captcha`, `login_wall`. The navigation agent still returns `NavOutcome`, but its state is advice only.

**Board route.** `board_routes` collects candidates from the page's own board, or, for a walled page whose board can't be told, from every board that can read a job id off the URL (at most `MAX_ROUTES` = 4). Greenhouse (`greenhouse_routes`): the id is `gh_jid`, or on a walled page a job-id-shaped number in the URL path; the board token is named in the page or guessed from the domain; the candidate is `embed/job_app?for=<token>&token=<id>`. `_open_board_route` loads each one in the browser and accepts the first for which `greenhouse_route_verified` holds (Greenhouse's host, the form signature, this job's id) and a form is visible; a closed-job page (`closed_url_patterns`, `error=true`) at an explicit candidate (id from `gh_jid`, token named by the page) with HTTP 200 ends the run `job_closed`. If nothing verifies, discover returns to the wrapper and the detail says `board route: none | unverified | closed on <token>`. No API or other side-channel HTTP is used.

## Conventions
- Board-specific knowledge goes in a `BoardProfile`, not in generic code; fixtures guard against cross-board regressions ([development](../development.md)).
- Models only get roles from `yahbah/llm/models.py` ([llm](llm.md)); prompts are in `config/prompts.yaml` (`oneshot_*`, `agent_*_task`, `option_pick`, `post_submit_judge`).
- Activities wrapping these stages: `src/yahbah/workflows/activities/browser.py` ([workflows](workflows.md)).

## Submit boundary
Roadmap A3/A4, contract [run-lifecycle](../contracts/run-lifecycle.md) §4/§6/§8. Principle: **code evidence decides, models advise; agents can never submit.**

### Control classifier (`controls.py`)
One JS definition decides what a click (or key) on an element would do: `submit`, `advance` (Next, Continue, Save, Review, Skip) or `other`.
- It resolves the control first: the nearest button-like ancestor (`button`, `a`, `[role=button|link]`, `[onclick]`, `input[type=submit|button|image]`). An option, radio, checkbox, combobox, select or plain input is never a button, whatever it says; a `<label>` is the control it activates.
- A **native submit** (`type=submit`, or a `<button>` with no type inside a form) is never `other`: `advance` when its label reads like a step button, else `submit`. A label alone decides only for controls with no structural signal (`type=button`, `role=button`, links, `onclick` divs). Labels are word matches ("Next month" is not an advance).
- `FIND_SUBMIT_JS` (the pipeline's own locator) uses the same classifier: among the `submit` controls in the form holding our fields, a native one whose whole label reads like submitting wins, else the only one. A step button is **never** the final submit: with only `Next`/`Continue` on the page the stage fails `submit_button_not_found` before anything is recorded. A disabled control is waited for (3 s), then `submit_button_not_found`.

### Agent guard and tripwire
- `GuardedTools(Tools).act()` runs before every agent action and answers a refusal as an error result. It refuses: a click on a `submit`/`advance` control; Enter (implicit form submission; allowed only in a textarea or an open dropdown, never with ctrl/cmd/alt) or Space on a focused submit/advance control; typing (`input`) into anything but a text control (a button, link, checkbox or select is a key press away from activating), in every mode, and a newline typed into a non-textarea; a coordinate click. The focused element is found through shadow roots and same-origin frames; focus in a frame that can't be inspected refuses Enter and Space (fail closed). In form modes it also refuses `navigate`, `search`, `go_back` and `close`. **Planned text only:** when `make_tools` is given a `FillContext` (the fix agent), `GuardedTools.text_allowed` is set to `FillContext.text_allowed`, and an `input` whose text is non-empty and not contained (normalized) in some planned value is refused with `VALUE_NOT_PLANNED` and logged to `guard.jsonl` like the other refusals.
- `run_agent(mode=...)` sets how strict it is: `navigate` (discover's navigation agent: clicking "Apply" on a job page must work, so controls are off limits only once the page looks like an application form, `discover.looks_like_form`, or the control sits in a `<form>` of its own with two or more fillable fields), `form` (default; mapping and dropdown agents: always off limits), `fix` (the fill-fix agent: as `form`, plus native `submit` events are cancelled at window level while it runs, and afterwards the **tripwire**).
- **Planned values, in every fill.** The fix agent's `fill_field` writes exactly the planned value of a field that has a plan entry (or an option that means it, `match_option`) and refuses a field without one ("has no planned answer; leave it alone and report it as unresolved") or a different value; `upload_document` only the document the field is planned for. This holds in the first fill (answered by the engine) and in the locked re-fill alike; the old unknown-key schema read in `fill_field` is gone. **Baseline, in every fill.** `fill_form` takes `FillContext.baseline` (`take_baseline`) once code has filled the form, new fields and option replans included and before any agent runs: for every field *without a planned answer* (no mapping, `skip`, or an empty value) a signature `[text, ticked, file count, shown text]` (`dict[str, str]`, field key -> JSON string). `problems_for` then reports, in every mode, such a field whose content differs from its baseline (`[key] "label": has no planned answer but its content changed to …`), whatever write path changed it. That closes the paths the `input` guard does not see (`send_keys`, `clear:false` fragments, `select_dropdown`, radio clicks, browser-use's own `upload_file`), so a first fill fails closed (`fill_failed`) instead of showing the reviewer an agent's stray write. The baseline is read in the same pass as the values it is compared with, so whatever the page did between two reads is not mistaken for an agent's write. `FillContext.locked` is set when there is no mapper (`map_new_fields=None`: the review re-fill and the submit step, where the mappings are the user's approved answers) and now governs only new-field handling and `problems_for`'s `wrote_from` check (a field whose last write came from something other than its approved answer is a problem), so neither the fill nor the submit gate reports clean for a form that differs from what the user approved. `FillOutput.baseline` is set after first fills too, but only the approved re-fill's is carried to the submit step (`SubmitInput.baseline`): `submit_and_verify` in locked mode without one fails closed (`fill_failed`, "no approved-state baseline") before the gate and the claim, because a baseline taken there would read agent text as a starting value. With it, the gate and every post-claim fix round check against it. The planned-text guard above is in addition to the baseline.
- Tripwire (`fix` only): if the document was replaced (a stamp on `window` is gone), the URL changed (fragment ignored) or the form's fields vanished, `StageFailed("possibly_submitted")`, also when the agent run ends in a cancellation (the activity must record the possible submission, not end the run CANCELLED). If a link opened another tab, focus is returned to the form's tab and that alone does not trip it. The activity records the possible submission and ends the run `SUBMIT_UNCERTAIN`.
- Limits (known): an unclassified control that submits by XHR without changing the DOM within the agent run is not seen; the mapping and dropdown agents have no tripwire (they run before anything is filled); the navigation agent may click a submit-looking control that sits outside any form on a page with fewer than three fields (one-click "Apply" sites are indistinguishable from navigation).

### `submit_and_verify` (`submit.py`)
```
submit_and_verify(session, board, ctx, email, already_attempted, claim, map_new_fields=None, beat=..., record=None) -> SubmitResult
```
1. **Gate** (nothing recorded): new fields are mapped and filled if there is a mapper, else a *required* one without an answer is `needs_answer`; empty/mismatched required fields or validation errors are `fill_failed`.
2. **Locate** the submit control (`submit_button_not_found`; nothing claimed).
3. **Claim**: `await claim()` once, right before the first click; `False` -> `claim_denied`, no click. Not called when `already_attempted`.
4. **Click**, then up to `settings.submit_max_attempts` **rounds**. A round waits until the page shows something decisive on two polls in a row, or `ROUND_SECONDS` (4 s) pass (a spinner, `aria-busy` or a disabled submit control extends that by up to 20 s), then judges the structural evidence (`assess`):

| verdict | meaning | action |
|---|---|---|
| `submitted` | our form's fields (fewer than half left) and the submit control are gone, no error text, and the visible text carries a confirmation phrase | success, no model call |
| `probable` | same, no confirmation phrase | success only if the model's advice is `submitted` (`decided_by: "code+model"`) |
| `errors` | the form is still there and validation errors were found in the DOM | fix (new fields, rewrite the fields the errors name, fix agent), re-gate, click again |
| `code_prompt` | verification-code inputs | fetch the code, enter it (read back), click again |
| `pending` | nothing decisive: a no-op click, "thank you" text with the form still there, an in-flight request | wait another round; **never click** |

   After the last round's re-click there is one more observation (`kind: "final"`). Still unproven: `StageFailed("submit_unverified")`; never a flagged result.
5. **Model advice** (`PostSubmitState`, driver, then vision if it fails or is inconsistent): asked only for `probable` and for a last-round `pending`. It can complete `probable` or name a blocker (`captcha`, `login_wall`, `job_closed`, `blocked`, used as the failure reason); a `submitted` it gives for a `pending` page counts for nothing. Its `problems` are recorded as quoted data and never reach an agent.
6. **Verification codes**: `GmailClient.wait_for_verification_code(email, since_epoch=<click>, subject_hint=board.email_code_subject, code_pattern=board.email_code_pattern, exclude_message_ids=<tried>)`. `finalize_code_message(id)` runs only once the page has moved on from the code inputs; a code the page keeps asking for again is *rejected*, never finalized, and the next message is fetched. No email in time: `email_code_timeout`; inputs that don't show the typed code: `email_code_entry`.

Everything after a `True` claim is `StageFailed` unless verified (`submit_unverified`, `fill_failed`, blocker reasons, `email_code_*`, `possibly_submitted`); unexpected exceptions (a click that raised, a lost CDP connection) are converted to `submit_unverified`. The caller ends such a run `SUBMIT_UNCERTAIN` and never clicks submit for it again. A server-side validation round trip that reloads the page loses the field keys; that is `submit_unverified` ("fields can no longer be addressed").

### Submit evidence record (`record`)
`record(dict)` is awaited once per observation: every verify round (`kind: "round"`), plus the closing pass after a last-round re-click (`kind: "final"`). A record that raises is logged and ignored. The same dict is `SubmitResult.evidence` for the closing observation. All values are JSON-serializable; page-derived strings (`signals.excerpt`, `signals.errors[].message`, `judge.problems`) are **untrusted data**: render as text only.
```json
{"schema": 1, "kind": "round|final", "round": 1, "at": "ISO-8601 UTC", "elapsed_s": 4.6,
 "clicks": 1, "attempt": "first|verify_only", "url_before": "…", "url": "…",
 "verdict": "submitted|probable|errors|code_prompt|pending",
 "decided_by": "code|code+model",
 "action": "accepted|waiting|fix_and_reclick|enter_code_and_reclick|stop",
 "signals": {"doc_replaced": false, "form_gone": true, "controls": 0, "controls_before": 13,
             "submit_control": {"present": false, "visible": false, "disabled": false},
             "errors": [{"key": "3", "message": "…"}], "code_inputs": 0, "in_flight": false,
             "confirmation_markers": ["thank you for applying"], "error_markers": [], "excerpt": "first 300 chars"},
 "judge": null,
 "code": null}
```
`judge`, when asked: `{state, blocked_reason, vision, problems[≤10, ≤200 chars], reasoning[≤300 chars]}`. `code`, after a code was entered: `{message_id, outcome: "accepted|rejected"}` (the code itself is never recorded). `clicks` counts submit clicks of this attempt.

### Fill evidence and new fields (`fill.py`)
- `submitted_values(ctx, values)` -> the contract §8 rows `{key,label,type,required,options,answer,source,basis,generated,written,page_value,ok}`. `answer` is the mapping's intended value (a document is its file name, never its path); `source`, `basis`, `generated` come from the mapping dict unchanged.
- `fill_form(..., map_new_fields=None)` leaves fields that appear while filling alone and records the **required** ones without a mapping on `ctx.unmapped_new_fields` (schema-row shape, dropdown options read); they are not `problems`. The caller (the activity) returns them and sends the run back to review. With a mapper they are mapped and filled as before. `submit_and_verify` runs the same check before the claim and, with no mapper, refuses (`needs_answer`).
- `match_option` (in `agent/options.py` with `norm`, `TRUTHY` and `FALSY`; pure, and shared with the answer checks so an answer is judged against a widget's options exactly as fill matches it) takes prefixes as whole words ("No" does not match "Now").

### Option-miss replan (`fill.py`)
When a planned value matches none of the live widget's options, the executor raises `NoMatchingOption(options)` (a `FillError`): always for a native select and a radio/checkbox group, for a custom combobox only if some option list was ever visible (otherwise a plain `FillError`, a browser problem). `fill_keys` records it in `FillContext.option_misses[key] = (value, options seen)`. In `fill_form`, after the new-field loop and **only with a mapper** (the first fill, never the locked re-fill), `replan_option_misses` sends each missed field back through `map_new_fields` once: a row with the options read from the page (≤40, `options_total` beyond that) and `feedback` "<value> matches none of this field's options; choose one of them."; the new mapping replaces the old one, its write records are cleared and the fields are written again. A second miss goes the ordinary fill-problem route to the fix agent, which can only write the planned value. An agent never picks the option. Fields that appear while filling carry `description` and `section` into the rows `map_new_fields` receives, and new comboboxes have their options read first.
