# LLM Layer (`src/yahbah/llm/`, `src/yahbah/agent/llm.py`)

All models are local Ollama. Nothing sends page or personal data to the cloud.

## Model roles (`llm/models.py`)
`Role = driver | prose | vision | escalation`. `spec(role)` / `ollama_options(role)` give fixed `num_ctx`, `num_predict` (4096; 6144 when thinking), `think`, `keep_alive`, so a model is always requested with identical options and never reloads mid-run.
- driver: `settings.model_driver` (default `qwen3-coder-next:latest`, ctx 40960): agent loops, HTML work, answer interpretation, verification and reselection, match score, page judging; text only.
- prose / vision / escalation: `settings.model_prose_vision` (default `qwen3.8:27b`, ctx 32768); escalation has `think=True`. The answer engine's compose pass and cover letters use prose.
Defaults live in `src/yahbah/config.py` (`Settings`); verify there, as they are tuning knobs.

## Clients
- `llm/client.py`: `OllamaClient(role)` with `generate_structured` (output constrained by a Pydantic JSON schema), `generate_text`, optional images. Raises `LLMError`; `LLMOutputTruncated(LLMError)` when the reply hit `num_predict` (`done_reason == "length"`), so a caller can retry smaller. `last_usage` holds `{prompt_tokens, output_tokens, secs}` of the last `/api/chat` reply (a missing key is `None`); the answer engine reads it for its call report.
- `agent/llm.py`: browser-use `ChatOllama` subclass for agent loops ([agent](agent.md)).
- `llm/logs.py`: per-run log dir `artifacts/<run_id>/llm/` (`raw.jsonl`, `steps/`, `js_calls.jsonl`) selected via a contextvar set at the start of each activity (`use_run_log_dir`, which also records the run id for `current_run_id()`); total `llm` logs capped at 250 MB (oldest pruned).

## Applicant profile (`llm/profile.py`)
One canonical profile and one serializer.
- **Profile:** the DB `applicant_profile` row (seeded from `personal.yaml`'s `profile:` by `scripts/seed_profile.py`).
- **`profile_facts(profile)`:** the profile fields as `key: value` pairs (`full_name`, `first_name`, `skills`, `bio`, `work_experience[i]`, `education[i]`; entries with `use_in_custom_prompts: false` are left out). `scalar_values` and the experience/education line helpers are reused by the fact catalog below.
- **`profile_text(profile, contact=True)`:** the only serializer of the profile as prompt text, one `key: value` line per entry (each `work_experience[i]` carries that role's bullets). Cover letters and the match score (`contact=False`) use it.
- **Freshness:** `config.load_prompts_config()` re-reads `prompts.yaml` and `personal.yaml` whenever either file's mtime or size changes, so an edited fact applies to the next plan without a worker restart. `load_prompts_config.cache_clear()` forces a re-read.

## Facts (`llm/facts.py`): what every answer rests on
The applicant's knowledge is a typed `facts:` list in the gitignored `config/personal.yaml` (template: `config/personal.example.yaml`) plus facts built from the profile. `load_facts(profile, account_email=None)` returns a `FactCatalog`: YAML facts first (file order), then profile facts. It raises `FactsConfigError` for an invalid list.
- **`Fact`** (frozen, `extra="forbid"`): `id`, `kind`, `value` (text, number, bool or `list[str]`), `data_type` (`text | boolean | number | date | relative_availability | list`), `description` (required), `aliases`, `examples` (example questions), `guidance`, `jurisdiction` (`^([A-Z]{2}|EU)$`), `applies_to`, `source` (`applicant_verified | profile`), `sensitivity` (`normal | legal | eeo`). `kind` is a free snake_case retrieval aid: nothing in code types a fact by its id or kind.
- **Value normalization** by `data_type`: YAML 1.1 reads `Yes` as true and `2026-01-15` as a date, so a `text` fact stores them as "Yes" / ISO text; `boolean` accepts a bool or yes/no/true/false; `number` an int, float or numeric string; `date` a date or `YYYY-MM-DD`; `list` requires `list[str]`; `relative_availability` a string.
- **Validation:** YAML ids are `^[a-z][a-z0-9_]*$` and unique; `source: profile` is rejected in YAML. `FactsConfigError` messages are built as `facts[i].<field>: <problem>` and never contain a value, so they are safe in `error_message`.
- **Placeholders:** a YAML fact whose value is empty, `<...>`, TODO/TBD/FIXME/lorem ipsum, `your ...`, all zeros, a 555-555-5555 phone or an example.com/org/net address is left out of the catalog (`FactCatalog.placeholders`; logged as `[facts] placeholder values ignored: <ids>`). It is therefore never citable and never in a model's id enum.
- **Profile facts** (`source="profile"`, ids `profile.<field>`): `full_name`, `first_name`, `last_name`, `email`, `phone`, `location`, `linkedin_url`, `github_url`, `portfolio_url`, `years_of_experience`, `skills`, `bio`, `work_experience[i]`, `education[i]`; empty values are omitted. `profile.email` is `account_email or profile.email`, so it is the run's alias and nothing overrides it later. The four whose `kind` is `skills`, `bio`, `work_experience` or `education` are the **profile records** (`PROFILE_RECORD_KINDS` in `answer_checks.py`): they list what the applicant has and can never support an absence on their own (check rules 8–10 below).
- **Catalog views:** `compact(ids)` is what a model sees to choose facts (no value); `blocks(ids)` is the full fact incl. value, guidance, `applies_to`, source and sensitivity; `values(ids)` is the value text, for number checks.
- **Legacy `known_answers:`:** `config._read_prompts_config` no longer reads it; it only sets `legacy_known_answers` when the key is still in `personal.yaml`, and `load_facts` then raises `FactsConfigError` with the migration steps ([development](../development.md#migrating-known_answers-to-facts-one-time-user-steps)). `yaml_fact_value(kind)` (first YAML fact of a kind, as text; `None` for none or an invalid list) serves the match score.

## Answer engine (`llm/answers.py`): two passes, grounded and checked
`AnswerEngine().plan(fields, job, catalog, *, prior=None, feedback=None)` returns an `AnswerPlan`: one `FieldMapping` per field in form order, the `unresolved` questions, per-field diagnostics, ignored placeholders and the model calls made. `JobContext(location, description, company=None, title=None)` carries the posting; all of it is untrusted page data, context only, never evidence. Pass 1 and Pass 2 show one `JOB (untrusted page data, never evidence)` section: `location`, `company` and `title` (each of the last two cut to 120 characters, `null` when unknown) and the trimmed description. The verifier's JOB section holds **only the location** (2026-11-08: in live iteration 3, showing it the hiring company made it reject correct answers that name the applicant's similarly named employer, 22 of 24 correct answers checked alone; the description stays out because it is untrusted page text). The activities build the context with `workflows.activities.llm.job_context(input)` from `job_location`, `job_company`, `job_title` and `job_description`. `prior` is a list of `FieldMapping` dicts already on the form (read: `key`, `label`, `value`), `feedback` a sentence per field key that goes to Pass 2. The B0 per-step loop can call it once per step. Callers: `map_answers_activity`, `map_new_fields_activity` and the fill-time mapper ([workflows](workflows.md)), plus `scripts/run_pipeline.py`.

**Flow:** code autofill → Pass 1 interpret → documents → Pass 2 compose → deterministic checks → verifier → at most one recovery round → plan.
1. **Code tier.** A field whose HTML `autocomplete` is `given-name`, `family-name`, `name`, `email`, `tel` or `tel-national` and whose profile fact exists becomes `source="autofill"`, `basis=[profile.<field>]`, with no model call.
2. **Pass 1, interpret** (driver, `answer_interpret`, batches of 40, each sees the whole form). Per field: `intent`, `document` (`resume | cover_letter | none`), `jurisdiction` (ISO code or `EU`; the job's country for an unscoped legal/work question), `qualifiers`, `fact_ids` (every possibly useful catalog fact, recall first) and `ambiguity`. It sees the fact catalog without values. The intent is written in the question's own terms (a notice period is not a start date) and **starts with `open-ended:`** for a question that wants the applicant's own words (motivation, behavioural, curveball, "anything else?"); a specific personal detail or a status/eligibility/availability/notice/salary question is not open-ended even in a text box. When the question names a specific technology, tool, product, certification or domain, the name stays in the intent, and `fact_ids` include every fact whose description or aliases mention it (that is how compose finds a stored "no professional X experience" fact). For an open-ended question `fact_ids` always include the bio, every work experience entry and the skills, and a playful question has `ambiguity` null. Duplicate entries for one id are merged (union of `fact_ids`, first intent), ids the reply missed get one `interpret_missing` call, then a default interpretation.
3. **Documents.** A file field routes to `resume` / `cover_letter` (value ""); a required file field with no document is `missing_fact` ("asks for a document YahBah doesn't have"), an optional one is skipped. A text/textarea field interpreted as `cover_letter` maps to `cover_letter`.
4. **Pass 2, compose** (prose, `answer_compose`, batches of 12 in form order; each batch sees earlier answers). Code retrieves the full blocks of the facts Pass 1 chose (`FACTS`); the rest of the catalog is shown as `{id, kind, description}` (`OTHER FACTS`) so a field can request more. A reply item is `{field_id, status, value, composed, evidence_ids, requested_fact_ids, requested_info, reason, quotes, absent}`; `quotes` (words copied exactly from the cited facts that the answer rests on, i.e. what was found) and `absent` (the thing looked for and not found, when the answer rests on it missing) default to empty / null for validation but, like every property, are required in the decoding schema. The prompt first classes each field **OPEN** (the applicant's own words; the `open-ended:` intent is only a hint, the question decides) or **FACT** (everything else, including every field with options and every checkbox, number, date, email, phone and URL field). An OPEN field is `answered` with `composed=true`, built only from the facts (bio, work experience), adding no employer, tool, hosting, number, date or personal detail, with `quotes` empty and `absent` null. **One exception, the named-thing rule:** when the question is about the applicant's experience with a specific named technology, tool, product, certification or domain that no fact in `FACTS` mentions (by that name or another name for the same thing), the field is not composed (no bridging to related work, no denial): `needs_more_evidence` if a fact in `OTHER FACTS` might mention it, else `missing_fact` with `requested_info` "Your experience with <the thing>, or that you have none". A required field then blocks as `needs_answer` with a `fact_template`; an optional one stays blank like any unresolved field. Once the user stores a fact that mentions the thing (even "No professional X experience; I deploy Y"), later applications compose an honest answer from it. General behavioural, motivation and personality questions with no such named thing are always composed from the bio and work history. A FACT field is `composed=false`: `answered` (value + `evidence_ids`, only ids listed in FACTS), `needs_more_evidence` (+ `requested_fact_ids`, instead of citing an id that is only in OTHER FACTS), `missing_fact` (+ `requested_info`, phrased as a fact to store) or `needs_clarification`. An answered FACT field that cites only the profile's skills, bio, work experience or education entries must give `quotes` (copied exactly, never a synonym or the question's own wording; "GCP" in the question with "Google Cloud" in the skills list is quoted "Google Cloud") or `absent`, whatever the answer's polarity; an absence never rests on those entries alone. Other stored facts may leave `quotes` empty. Value formats follow the widget (verbatim option text; `yes`/`no` for a single checkbox; `YYYY-MM-DD`, `YYYY-MM`, `HH:MM`, digits). FACT reasoning rules: **never answer from absence** (a listed skill or employer can give "yes"; an unlisted one is `missing_fact`, never "no", unless a fact states it, declares the list complete or states something incompatible with "yes"); a boolean fact's value, not its description, holds; **a fact's guidance is binding** (what it says it does not mean, it does not answer); answer the question's own concept (notice period ≠ start date ≠ availability after an offer; salary expectation ≠ current salary); negation, thresholds, jurisdiction, citizenship ≠ residence ≠ authorization, sponsorship ≠ authorization, no calendar date from relative availability, EEO only from a fact about that attribute, consent only from a fact that covers it.
5. **Checks** (`llm/answer_checks.py`, pure; below), then the **verifier**.
6. **Verifier** (`verify_answers`, prose role `qwen3.8:27b` since 2026-11-08, `answer_verify`, batches of 20): an independent call that sees the job's location and each answer with its question, jurisdiction hint, qualifiers, `quotes`, `absent` and the cited facts in full. Its verdict is `{field_id, supported, problem}` (verdict first: the reason-first order tried in iteration 3 made it argue itself into rejecting correct answers). It checks in order: what the question asks in its own terms; whether each fact's description and guidance (binding; checked for every cited fact that has guidance, routine answers included) cover exactly that; whether the value follows from the fact values (a boolean fact's value decides over its description), and, **with quotes, whether the quoted words establish this answer to this question** (another name for the same thing counts: "Google Cloud" answers a GCP question; a similar-looking different thing, Java for JavaScript, or a similarly named different organisation does not); and whether a "no / none / never" about experience, employers, skills or history, or an `absent`, has a cited fact that states it or states that the list it rests on is complete (lists of work, skills, education and projects never state what the applicant has not done, so an absence resting only on them is unsupported). It decides the jurisdiction itself (the hint is only a hint) and rejects evidence about another country or attribute, an inferred demographic attribute and a calendar date derived from relative availability. A composed answer is judged only on what it literally states about the applicant (it may rephrase, express motivation, talk about the company and role, and describe how the applicant works) and is unsupported if it states an applicant fact not in the evidence, or if it claims or denies experience with a specific named technology, tool, product, certification or domain that no cited fact mentions (offering other work in its place counts as a claim). A missing verdict counts as unsupported ("no verdict"). Only answers with no check problems are sent to it.
7. **Classification.** Accepted (answered, no problems, supported) → `FieldMapping(source="answer", basis=<evidence ids>, generated=composed)`. `needs_clarification` is final. Any other failure: a required field joins the recovery set; an optional one becomes an unresolved entry plus a `skip` mapping.
8. **Recovery, once.** For each required field: requested fact ids that were not shown are added to what it sees; if none, one `reselect` call (driver, `answer_reselect`) looks through the catalog for facts not yet shown; a field that still has nothing new is final `missing_fact` with Pass 2's reason. An answered field whose problem is `cites_unshown` gets every cited id that is in the catalog but was not shown added to what it sees (no extra call, still inside the one round), with the feedback "The facts you cited without having been shown them are now shown in full; cite a fact only if its content supports the answer." plus its other problem messages; the verifier still checks the result. Then one `recompose` (Pass 2 prompt) over the rest, each carrying `feedback` (the problem, the verifier's message, or "More facts are now shown for this field."), the checks again and a `reverify`. There is no second round.
9. **Unresolved rows.** `status` is `missing_fact | needs_clarification | unsupported | invalid_value` (check problems `uncited`, `cites_unshown`, `unsupported` and a verifier rejection → `unsupported`; `invalid_value` stays itself). `reason` is one sentence; reasons, requested info, intents and verifier problems are scrubbed of any text fact value (4+ characters) before they reach the `answer_plan` artifact (`error_message` carries only labels and statuses). For `missing_fact` (non-document) and `unsupported`, `fact_template` is a paste-ready YAML skeleton (`id`/`kind` from the intent or label, empty `value`, `description` from the requested info, `jurisdiction` when known) that the run page shows.

`AnswerPlan.blocking` is the required unresolved rows; `raise_if_blocked()` raises `NeedsAnswer`, whose message is `needs_answer: <label> (<status>); …`, so a run's `error_message` lists every blocking question without values. Fail closed: a required question the facts cannot support ends the run `FAILED` / `needs_answer`; an optional one is left blank.

**Deterministic checks** (`check_answer(field, value, composed, evidence, shown, catalog, *, intent, quotes=(), absent=None) -> (value, problems)`), in order:
1. empty value → `invalid_value`;
2. evidence not shown for this field or not in the catalog → `cites_unshown`;
3. `composed` on a field that is not free text (`text`/`textarea` without options) → `uncited`;
4. non-composed with no evidence → `uncited`;
5. widget check: an option field with a complete option list (`options_total` ≤ shown) must match an option via `match_option` (otherwise fill matches at write time); a single checkbox must read yes/no; `date` is a real `YYYY-MM-DD`, `month` `YYYY-MM`, `time` `HH:MM`, `number` numeric, `email`, `tel` and `url` shaped → `invalid_value`;
6. a `date` or `month` value must appear verbatim in a cited fact → `unsupported` (never a calendar date from relative availability);
7. numbers (`grounding.unsupported_numbers`): a composed answer is checked against the label, description, options and every fact, and sentences with unsupported numbers are dropped (nothing left → `invalid_value`; the repair is recorded); a non-composed answer is checked against the label, description, options and its cited facts → `unsupported`;
8. each **quote** (`quotes`, the words of a cited fact the answer rests on) must appear in a cited fact: a profile record's value, or a stated fact's value or description (a boolean's value is only `true`/`false`, so its words are in its description; amended 2026-11-07 after the first live run, where value-only matching rejected every quoted boolean). `norm()` forms (`agent/options.norm`), whole-word phrase match, list values joined → `unsupported` ("a quoted phrase isn't in the cited facts; copy it exactly as written there"). The quote "Postgres" against a skills list that says "PostgreSQL" fails: the model must quote "PostgreSQL", and the verifier judges that this answers a Postgres question;
9. **`absent`** (what the answer rests on not finding) given while every cited fact is a profile record → `unsupported` ("an answer resting on something missing from the profile needs a stated fact that says so or that the list is complete");
10. a non-composed answer whose cited facts are all profile records, with neither `quotes` nor `absent` → `uncited` ("say which words in the profile the answer rests on (quotes) or what was not found (absent)");
11. a composed answer to a free-text field whose Pass 1 `intent` does not start with `open-ended:` (`OPEN_ENDED`) → `invalid_value` ("only an open-ended question gets a composed answer; answer this field from its facts"), so a fact field is never answered with prose labelled `generated` (added 2026-11-07 after a whole-form run composed the answer to "Briefly describe your US work authorization status"). It goes through the normal recovery round.

**Profile records** are the facts with `source == "profile"` and `kind` in `PROFILE_RECORD_KINDS` (`skills`, `bio`, `work_experience`, `education`): lists of what the applicant has, whose silence is no evidence of absence. Rules 8–10 do not care whether the answer is yes or no: "Do you lack PostgreSQL experience?" → "No" with quotes `["PostgreSQL"]` citing `profile.skills` passes; "Are you unfamiliar with TypeScript?" → "Yes" with `absent: "TypeScript"` citing only `profile.skills` is rejected. A "no" that rests on absence therefore needs a stored fact that states it or declares the list complete (`employment_history_complete` for "have you worked for X before"). These checks are bookkeeping only: **code checks bookkeeping, models judge meaning.** Whether "Postgres" and "PostgreSQL" are the same thing, whether Java is JavaScript, whether the "Acme" in a question is the applicant's Acme or the hiring company given the job, and whether a stored fact establishes an absence are model judgments (Pass 2 and the verifier); there are no synonym tables and no deterministic equivalence rules. The check messages are fixed strings (no fact values), and `quotes` and `absent` are never written to the `answer_plan` artifact (a quote is fact text); only the fixed problem messages reach its `checks`.

**Prompt budget and retries.** Prompts are JSON sections ("HEADER (JSON):" then one line). Estimated tokens = characters / 3.5 against `num_ctx − num_predict − 1024`. Over budget, trim in order: the job description to 2000 chars, the fact catalog / other facts to `{id, kind}`, the FORM to the batch's fields; then split the batch recursively; one field still too big raises `LLMError("prompt too large for <role>")`. A truncated compose or verify reply on more than one field splits the batch in halves; any other `LLMError` is retried once, then raised for the activity's Temporal retry policy. Every id and fact id in a reply is a schema enum built per call (so a model cannot name a field or fact that was not offered), and every property is required in the decoding schema.

**Call budget.** Typical form: 3 model calls per batch (interpret, compose, verify); worst case 6 (adds reselect, recompose, reverify; `interpret_missing` can add one). `AnswerPlan.calls` records step, role, fields, secs and tokens per call.

**`answer_plan` artifact.** One per plan (`AnswerPlan.to_artifact(stage, review_round)`, stages `map_answers | fill | map_new_fields`): per-field status, source, basis, intent, jurisdiction, fact ids, checks, verifier outcome and `recovered`/`repaired`, the unresolved rows (with templates), placeholder ids and the call report. It holds fact ids, never fact values ([contract §8](../contracts/run-lifecycle.md)).

## Match score (`llm/match_score.py`)
`compute_match_score(profile_summary, job_description) -> (score 22–99, rationale)`: one driver call (`match_score` prompt, `_MatchScoreResponse`), with the salary expectation taken from the first YAML fact of kind `salary_expectation` (`yaml_fact_value`). Callers: `map_answers_activity` (profile text without contact details) and `gmail/alert_parser.score_job`. The decomposed scorer is roadmap B-level work (audit LLM F3).

## Cover letter (`llm/cover_letter.py`)
- `cover_letter_requested(field_mappings)` is true when a field maps to `cover_letter`. The workflow runs GENERATE_COVER_LETTER only then; otherwise FILL and SUBMIT get no cover letter (a cover-letter field that first appears during fill is then skipped if optional, a fill problem if required).
- `CoverLetterGenerator.generate` (prose model):
  - Input: `profile_text(contact=False)`.
  - System prompt: the style prompt `cover_letter` (`personal.yaml` overrides the default in `prompts.yaml`), with the fixed `cover_letter_rules` (grounding) always appended.
  - The letter gets the same number check as generated answers: one rewrite, then the offending sentences are dropped.
- PDF rendering with fpdf2 lives in the `generate_cover_letter_activity`.

## Tests and eval
- **Offline**, with `ScriptedLLM` and the synthetic applicant (`test/harness/profile.py` `SYNTHETIC_FACTS`): `test/yahbah/llm/` (`test_facts.py`, `test_answer_checks.py`, `test_answer_engine.py`, `test_profile.py`, `test_migrate_known_answers.py`) and the adversarial invariants in `test/invariants/task5_answer_integrity/` (a choice answer with no evidence never becomes a mapping; evidence not shown is rejected; placeholder facts are absent from the catalog and the Pass 1 enum; JD bait answered without evidence → `NeedsAnswer`; a verifier rejection that survives recompose → `NeedsAnswer`; the recovery round is bounded to one; an edited fact changes the next plan; an invented number is dropped; `composed` on a radio is unsupported; relative availability never yields a date; `to_artifact` holds no fact values). The harness has builders for scripted replies (`interpret_all`, `compose_all`, `verify_all`, `reselect_all`, `prompt_section`, `asked_ids`).
- **Live answer eval** (opt-in, needs Ollama with both models): `YAHBAH_EVAL_OUT=artifacts/eval/answers-two-pass.json uv run pytest -m live_llm test/yahbah/llm/test_answer_eval.py -s`. `answer_eval.yaml` holds a typed synthetic applicant (14 facts) and 69 items over three jobs (US, Munich, adversarial JD): screening facts and traps, jurisdiction and JD-injection traps, plain facts, personal-detail traps, `experience_trap` items (an open-ended question about a named technology no fact mentions), curveballs, STAR questions and document uploads. An item may carry its own `facts:` list (same shape as `applicant.facts`, seen by that item only; in `whole_form` mode items are grouped into forms by job + facts, so no other item sees them): the main set uses it for an employment-history-complete fact and for a stored fact that denies AWS work. Two modes: `per_item` (each item as a one-field form) and `whole_form` (all items of a job as one form, once per job).
- **Held-out set** (`YAHBAH_EVAL_SET=heldout`): `answer_eval_heldout.yaml` holds 20 items in the same schema, run by the same harness in both modes with the same gates (it reuses the main file's `applicant:` and adds the `zurich` job). `YAHBAH_EVAL_SET` is `main` (default) or `heldout` and picks the one set that runs; the other set's test is skipped. It exists to measure generalization of the prompts, so **it is never used to tune them**: run it once per prompt revision and report the result; a failure there is fixed against a new item in `answer_eval.yaml`, and the held-out set stays unchanged. Its author did not read `config/prompts.yaml` and prompt editors do not read it. `test_heldout_items_are_new` checks that it shares no item id, label or job with the main set, and `test_dataset_is_well_formed` checks both sets offline.
  - **Gates, in both modes:** 0 critical-fact errors (a wrong or unbacked fact answer, any answer to a trap, a wrong document source); `needs_answer` recall ≥ 95% on `screening_trap` + `personal_fact` + `experience_trap`; 100% of curveball and behavioural items answered, `generated=True`, with no unsupported numbers or forbidden phrases (an item with `basis_any` must also cite one of those facts); ≥ 95% of `screening_fact` + `fact` items answered (no unnecessary abstention); 0 `LLMError`s.
  - `YAHBAH_EVAL_REPEATS` sets the repeats and `YAHBAH_EVAL_OUT` a JSON report, which adds per-step mean/max seconds and tokens and the calls per form from `AnswerPlan.calls`.
- **Live verifier eval** (opt-in): `uv run pytest -m live_llm test/yahbah/llm/test_verify_eval.py -s` runs `AnswerEngine.verify_answers` on 55 synthetic proposals in `verify_eval.yaml` (29 seeded wrong: wrong jurisdiction, wrong attribute, invented facts, inferred EEO, a calendar date from relative availability, answers resting on absence from a list, absence disguised as a quote of what the list does hold, a quote that names a different thing, residence taken as agreement to travel or on-call, mentoring taken as managing; 26 correct, including inverse-polarity "No" answers and composed answers that name the hiring company next to the applicant's similarly named employer). A proposal may carry `quotes` and `absent` like a real one. Two modes, each with its own gates: `batch` (one `verify_answers` call per job) and `single` (one call per proposal, as a one-field form or a recovery round is). Switches: `YAHBAH_VERIFY_MODES` (default `batch,single`), `YAHBAH_VERIFY_ROLE` (`driver` | `prose`, test-only override of `VERIFY_ROLE`; the report records the model, so a `MODEL_DRIVER` override shows), `YAHBAH_EVAL_REPEATS`, `YAHBAH_EVAL_OUT` (written before the gates are checked). **Gates per mode:** catch rate ≥ 90% on the wrong ones, false rejection ≤ 10% on the correct ones. The code checks and the fail-closed rule are not relaxed to compensate for a miss.

## Limits
- **Retrieval depends on the facts' descriptions:** Pass 1 and the verifier read `kind`, `description`, `aliases`, `examples` and `guidance`, not code. A fact with a vague description is found less often; a question outside every fact becomes `missing_fact` and a skeleton in the run page, and the user adds the fact.
- **Semantic support rests on the models:** code checks citations, widget validity, dates, numbers, and the bookkeeping of quotes and absences (checks 8–10); whether a cited fact or quoted phrase entails the answer (same thing under another name, different thing under a similar name, an absence a stored fact establishes) is the verifier model's call (one independent pass, one recovery round). The batch-2 `auto_reviewed` reviewer pass is meant to add a further check, and review is the final gate.
- **A "no" about experience needs a stored fact:** an absence never rests on the skills, bio, work or education lists alone, so questions like "have you worked for X before?" or "do you have experience with Y?" block as `needs_answer` until the user stores a fact that states it or declares the list complete (`employment_history_complete`; a fact like `kubernetes_experience` in `config/personal.example.yaml`). Expect more `needs_answer` runs than with a model that guesses; that is the intended trade.
- **Inconsistent profile sources:** the alert-time match score still builds its own profile text from YAML (`gmail/alert_parser.build_profile_summary`) instead of `profile_text`.
