## Summary

The fill layer is a sound design for Greenhouse-class pages: per-type executors, read-back verification, a code-computed required-field gate, `submit_attempted_at` written before the click, and no submit tool for agents. It is also almost entirely unexercised. The database holds 336 runs, all from the pre-revamp stack (2026-03-31 to 2026-06-15, states `EXTRACT_FORM`/`MAP_FIELDS`/`FILL_AND_SUBMIT`); none has `submit_attempted_at` set and none has ever reached the new `MAP_FORM`/`FILL`/`SUBMIT` states. The only live evidence for the new path is four `_observations.jsonl` rows (one 13-field Greenhouse form) and six `debug-*` dirs. Tests cover pure helpers plus typing and upload on one static snapshot; none of the executors (`choose_combobox`, `choose_in_group`, `set_checkbox`, `select_native`), `fill_form`, `fill_new_fields`, `fix_with_agent`, `FIND_SUBMIT_JS` or `submit_and_verify` is referenced by any test.

Against the product vision (arbitrary sites, Workday next) the weak points are concentrated at the edges of the safety design, not in the happy path. Outcome and re-click decisions rest on one LLM verdict with no structural evidence (F1). An uncertain submission is stored as an ordinary `FAILED` run that the alert poller, duplicate check and retry route will happily run again (F2). Multi-step wizards are not modelled and a lone "Continue" is treated as the final submit (F3). The schema reader cannot see common ARIA-pattern controls, so the gate cannot flag them (F4). The agent submit guard misses click-handler submit buttons (F5). Each of these was reproduced or traced in code, and each is cheap to fix before the first live non-Greenhouse submission.

## Findings

### F1. Submit outcome and the second Submit click are decided by one LLM verdict, with no structural evidence required
- **Priority:** Critical
- **Confidence:** Confirmed defect (gate logic reproduced with local pages; how often the judge model gets it wrong is unmeasured)
- **Issue or opportunity:** `submit_and_verify` accepts `state="submitted"` and re-clicks Submit on `needs_fix` based on the driver/vision verdict, and the code-side cross-check (`contradicts`) is too narrow to catch the dangerous cases:
  1. `submitted` is accepted when the full form is still on the page with a visible Submit button, as long as there are no validation errors and no code inputs. Nothing requires the URL to change, the form to disappear, or a confirmation marker to exist.
  2. `needs_fix` triggers a second click as long as the verdict lists any problem (the LLM's text) and the code-side `current_problems()` is empty. Validation errors are not required, despite the docstring ("only ever clicked again with affirmative evidence the form is still waiting (a code prompt or validation errors)").
  3. The first look happens after a fixed `asyncio.sleep(3)`. `PostSubmitState` has no "pending/in progress" value, so a slow but successful submit (spinner, form still visible) must be classified as one of `submitted | needs_fix | email_code | blocked`; `needs_fix` leads to a second click.
  4. Page-derived text flows through the verdict's `problems` into the fix-agent task (`submit.py:285`, `fill.py:553-565`): untrusted content steering an agent that has generic click tools.
  5. After the last round the loop still re-clicks (`submit.py:289-291`) and then raises `submit_unverified` without checking what that final click did.
- **Evidence:**
  - `submit.py:136-144` (`contradicts`: `submitted` only contradicted when `form_fields_present and (errors or code_inputs)`); `submit.py:261` (fixed 3 s sleep); `submit.py:105-117` (4 states, no pending); `submit.py:284-291` (needs_fix then click); `submit.py:293`.
  - Probes P1-P4 are in `probe.py`, `probe2.py`, `probe3.py` under the session scratchpad `/private/tmp/claude-501/-Users-alex-Documents-YahBah/507601a9-f685-4b67-b6bc-a4c95c794a1d/scratchpad/application-forms-engineer/` (local pages in `pages/`; no network beyond 127.0.0.1, no LLM calls). Probe P4 (pure Python): `contradicts(submitted, Signals(form_fields_present=13, submit_button_visible=True, errors=[], code_inputs=0))` returns `False`.
  - Probe P3 (headless Chrome on a local mock ATS whose success page appears 6 s after the click; `OllamaClient.generate_structured` stubbed to return `needs_fix` once, then `submitted`; `fix_with_agent` stubbed to a no-op): the page registered 2 submit clicks. The only precondition is one wrong `needs_fix` verdict on an in-flight page, which the 4-state schema makes plausible. Upper bound with `submit_max_attempts=4`: 5 clicks.
  - Live evidence for the judge's accuracy does not exist (no run has used the new submit path).
- **Impact:** Two opposite failures on unfamiliar sites, which is exactly the product goal. A false `COMPLETED` loses an application silently, because `COMPLETED` is what dedupe treats as "applied". A false `needs_fix` sends a second application. Greenhouse's form-replaced-by-thank-you page masks the problem; slow SPAs, wizards and inline-confirmation sites do not.
- **Proposed resolution:** Make structure authoritative and the model advisory.
  - Compute `SubmissionEvidence` in code: URL changed (host or path), keyed fields gone, CTA gone or disabled, no errors, no code inputs, optional per-board `confirmation_js`. Accept `submitted` only if the model says so and the evidence agrees; otherwise treat it as `pending`, escalate to vision, or end `submit_unverified`.
  - Replace the fixed sleep with condition-based waiting (poll for URL/DOM/CTA change, or CDP lifecycle/network idle, with a bounded timeout). Add a `pending` state and never re-click while the CTA is disabled, `aria-busy` is set, or a request is in flight.
  - Allow a re-click only on code-derived evidence: `s.errors` non-empty, a non-empty `current_problems()` that the fix then clears, or `code_inputs > 0` for the email-code path. LLM `problems` become hints for the fix agent only, and they are passed as quoted data, not as task instructions.
  - Verify after the last re-click (one more evidence pass) before raising.
  - Persist per-round evidence (signals, verdict, screenshot path, timings) as a `submit_rounds.json` artifact; today only logs hold the reasoning.
- **Failure scenario & validating test:** Mock-ATS fixture server (seed: `pages/mock_ats.html` and `probe.py` in the scratchpad) with scripted behaviours, judge scripted per case: (a) slow success (6 s) must produce exactly one click and `COMPLETED`; (b) click that does nothing, with a judge saying `submitted`, must end `submit_unverified`, not `COMPLETED`; (c) a `needs_fix` verdict with no page errors must not re-click; (d) the last round's click is followed by an evidence pass. Assert click counts through a page-side counter.

### F2. An uncertain submission is not a durable outcome, and three code paths will submit that job again
- **Priority:** Critical
- **Confidence:** Strongly supported risk (traced across five files; not run end to end because the new path has never produced a live run)
- **Issue or opportunity:** Every uncertain exit of the submit stage collapses into `status="FAILED"`. The only discriminator is `submit_attempted_at`, which no dedupe or retry path consults.
  1. `check_duplicate_activity` treats only `COMPLETED` runs as "already applied" (`db_ops.py:262,284`).
  2. The alert poller's "already applied" check excludes `FAILED` (`alert_poller.py:298`), so the next alert email containing that URL creates a fresh run, which fills and clicks Submit again, with a different per-run alias.
  3. `POST /runs/{id}/retry` reuses the row, resets status, error and artifacts, but not `submit_attempted_at`, `is_test_run`, `confirmation_html` or `email_confirmed_*` (`runs.py:361-366`). In the new run `already=True`, so `submit_and_verify` skips the gate and the click and only "verifies" a freshly filled, never-submitted form (the CTA is not stamped, so `submit_button_visible` is false and no re-click can happen). The best case is a dead-end `submit_unverified`; the worst case is the F1 false `submitted`. It also deletes the DB artifact rows that were the evidence of the first attempt.
  4. The uncertain exits are: `submit_unverified` (rounds exhausted, judge failed, browser lost), CDP or Chrome errors after the click (plain exceptions, retried once with a dead session), the 45 min activity timeout, and `worker.fail_incomplete_runs` marking every `RUNNING` run `FAILED` regardless of `submit_attempted_at` (`worker.py:51-76`).
  5. `mark_attempted()` runs before the submit button is located (`submit.py:256-258`). When `click_submit` raises `submit_button_not_found` (see F3), the marker is written for a click that never happened, which then makes retries "verify-only" forever.
  6. Evidence retention is thin: `SubmitOutput.confirmation_url` is returned but the workflow ignores it (`application.py:184-199`) and nothing writes `run.tracking_url` (8 of the 30 historical completions have one, all from the old stack). Only `confirmation_html` (first 4000 chars of `main`/`body`), text and a screenshot are kept.
  7. Inverse risk: a testing-mode dry run ends `COMPLETED` with `is_test_run=True`, and both dedupe paths count it as applied, so a dry run can block the real application (and a real retry of a test run keeps `is_test_run=True`).
- **Evidence:** `workflows/activities/browser.py:279-344`; `submit.py:249-258,289-293`; `db_ops.py:262,284`; `gmail/alert_poller.py:290-301`; `api/routes/runs.py:340-400`; `worker.py:51-76`; `application.py:182-199,207-214`; the frontend only types `submit_attempted_at` (`frontend/src/lib/types.ts:67`) and never uses it. Probe P2 (see F3) reproduces the marker-before-locate ordering: a page whose only action is `type=button` "Next" makes `FIND_SUBMIT_JS` return `null`, so `click_submit` raises after `mark_attempted()` already ran. The DB read confirms there are currently zero attempted runs, so this has not bitten yet.
- **Impact:** Violates two stated invariants (no duplicate submission; correct handling of uncertain outcomes). The duplicate path needs no failure injection beyond one ambiguous outcome plus a repeated job alert, which is normal behaviour for alert feeds.
- **Proposed resolution:**
  - Add a first-class outcome, for example `SUBMIT_UNCERTAIN` (or a separate `submission_state`: `not_attempted | attempting | uncertain | confirmed | failed_with_evidence`). The workflow maps the non-retryable `submit_unverified` error and the worker-restart sweep to it instead of `FAILED`. Owner: temporal-platform-engineer, with a migration.
  - Treat `submit_attempted_at IS NOT NULL` (anything other than `failed_with_evidence`) as applied in `check_duplicate_activity`, the alert poller, `POST /jobs`/`submit_job_for_application`, and `retry_run`; exclude `is_test_run` runs from "applied". A deliberate human override (explicit `force_resubmit`) is the only way past it.
  - Reorder the submit step: locate the CTA, then `mark_attempted`, then click. Consider splitting the marker into "attempt started" and "click dispatched".
  - Write `confirmation_url` to `tracking_url` and keep the per-round evidence from F1 as artifacts. Do not delete evidence rows on retry.
  - Reconcile with the confirmation email (`email_confirmed_at`): an alias-matched confirmation should upgrade `uncertain` to `confirmed` (gmail-job-discovery-engineer).
- **Failure scenario & validating test:** (a) Run the submit activity against the mock ATS with a judge that raises on the first round; assert the run lands in the uncertain state, not `FAILED`. (b) Feed the alert poller and `check_duplicate_activity` a job whose previous run is uncertain; assert no new run. (c) Retry an attempted run through the API; assert 409 without override. (d) A page with only `type=button` "Next" must leave `submit_attempted_at` null.

### F3. Multi-step wizards are not modelled, and a lone "Continue" is clicked as the final Submit
- **Priority:** High
- **Confidence:** Confirmed defect for the button selection (reproduced); strongly supported risk for the downstream false success
- **Issue or opportunity:** The pipeline assumes a single page: one `get_form_schema`, one CTA, one gate. `FIND_SUBMIT_JS` picks a button whose label matches `submit|apply|send|complete application|finish`, and otherwise falls back to the only `type=submit`/untyped button regardless of its label (`submit.py:64-68`). On a wizard step that has a single "Continue" `type=submit`, that button becomes `submit-cta`, `submit_attempted_at` is written, and the click is treated as the irreversible final submit. A "Next" with `type=button` is not found at all (`submit_button_not_found`, after the marker was written, F2.5). When the step changes, all keyed step-1 fields leave the DOM, so `form_fields_present` becomes 0, which is the same signal that normally means success, so `contradicts` cannot flag a wrong `submitted`. Today's accidental progress through steps relies on the judge saying `needs_fix` ("a new required question") so that `fill_new_fields` maps the next step, bounded by `submit_max_attempts=4` rounds.
- **Evidence:** Probe P2 on local pages: `wizard1.html` (one "Continue" `type=submit`) gives `FIND_SUBMIT_JS` = `'Continue'`; `wizard2.html` ("Save for later" + `type=button` "Next") gives `null`; `mock_ats.html` gives `'Submit application'`. Code: `submit.py:56-74,256-258,261-291`; `fill.py:585-600`. The wiki records that Workday and Lever run as `generic` and Workday is the named next target (it is a multi-step, account-gated wizard).
- **Impact:** Workday-class forms (and iCIMS, Taleo, SmartRecruiters-style flows) cannot be completed reliably; on the accidental path a wizard's last step is also reached with no per-step gate. A "Next" click recorded as a submit attempt poisons the run's idempotency state.
- **Proposed resolution:** Add a step-aware form loop in code, not a new agent. Classify each candidate button as `advance` (Next/Continue/Save and continue/Review), `submit` (final) or `other` (Back/Save for later/Cancel), using page cues rather than the label alone (step indicator, presence of Back, `aria-current=step`, whether it is the last step). Per step: map and fill the visible fields, run the gate, click `advance`, wait for a DOM change, re-read the schema, repeat. Only the final `submit` goes through the existing gated path and writes the marker. When the classification is ambiguous, stop and hand off to a human instead of clicking. Add per-board hooks (`BoardProfile`) for step buttons; build a saved Workday fixture before any Workday-specific code.
- **Failure scenario & validating test:** Local 3-step wizard fixture (seed: `pages/wizard1.html`): assert that steps 1-2 never write `submit_attempted_at`, each step is gated and verified, the final submit is clicked exactly once, and an ambiguous last step ends in a human-handoff outcome.

### F4. The schema reader cannot see common ARIA-pattern controls, so they are neither filled nor gated; typed-input constraints are invisible
- **Priority:** High
- **Confidence:** Confirmed defect (coverage reproduced on a synthetic page); real-world prevalence per ATS is a hypothesis, and only Greenhouse has been exercised live
- **Issue or opportunity:** `READ_FORM_SCHEMA_JS` scans `input, select, textarea, [role=combobox]` in the top document only (`tools.py:76`). The required-field gate (`problems_for`) only knows keys in `ctx.fields`, so a required control the schema misses is not even reported as empty, and the first Submit click goes out incomplete. Server-side validation then drives the F1 `needs_fix` loop. Separately, the schema carries no constraint metadata, so values are written blind: `fill_text` returns the value it intended to write even when the browser rejected it, and read-back detects the mismatch only after the fact, with a retry that repeats the same write.
- **Evidence:** Probe P1 (`pages/widgets.html`, real `get_form_schema`): 3 of 10 controls were returned (plain text, `type=date`, native select). Missing: `role=radiogroup` with `role=radio` divs, `role=checkbox`, `button[aria-haspopup=listbox]` dropdown, `contenteditable` rich-text, an open shadow-DOM input, an input inside an iframe. Probe `probe2.py` (`pages/typed.html`): a non-ISO value written to `type=date` leaves the page value empty (`value_ok=False`, and the retry path rewrites the same string); a 60-character answer into `maxlength=20` is silently truncated to 20 (`value_ok=False`; the fix agent is told to use only the listed values, so it cannot shorten). `fill.py:328-331,337`; `FormField` (`schemas.py:13-21`) has no constraints. `run_js` evaluates in the main frame only (`tools.py:153-168`); iframes are handled only for registered boards by opening the embed URL.
- **Impact:** Ashby-style Yes/No buttons, Workday-style `aria-haspopup` dropdowns, rich-text cover-letter boxes and iframe-hosted forms (iCIMS, some embeds) fall outside both the fill and the gate. Date and length constraints turn otherwise answerable runs into `fill_failed`.
- **Proposed resolution:**
  - Extend the reader (and matching executors with read-back) for `role=radio(group)`, `role=checkbox|switch`, `button[aria-haspopup=listbox]`, `contenteditable`/`role=textbox`, open shadow roots, and same-origin or CDP-target iframes. Share it with browser-navigation-engineer since `get_form_schema` lives in `tools.py`.
  - Add a coverage tripwire to the gate: count all required-looking controls in the page (`[required]`, `[aria-required=true]`, including shadow roots and frames) and refuse to click Submit when some are not covered by `ctx.fields`.
  - Add `FormField.constraints` (`maxlength`, `pattern`, `min`/`max`, `placeholder`, `inputmode`). Normalise at write time (date to ISO via a real parser, failing loudly if unparseable), return what the page shows instead of what was intended, and pass `maxlength` to the answer generator so it writes a shorter answer rather than truncating (llm-intelligence-engineer owns that half).
- **Failure scenario & validating test:** Add `widgets.html` and `typed.html` as fixtures with expected schema output and per-widget fill and read-back tests; assert that the gate blocks submit when an uncovered required control exists.

### F5. The agent submit guard does not cover click-handler Submit buttons
- **Priority:** High
- **Confidence:** Confirmed defect in the guard (reproduced); whether a local fix agent ever clicks Submit is a hypothesis
- **Issue or opportunity:** `fix_with_agent` runs the generic browser-use agent with every default action except `evaluate` (`tools.py:355`), including `click` and `send_keys`. `GUARD_SUBMIT_JS` disables only `form button[type=submit]`, `form input[type=submit]` and `submit-cta`, and cancels `submit` events at window capture. A SPA submit button that is `type=button` with an `onclick` handler, or a `div role=button`, neither fires a form `submit` event nor matches the selector.
- **Evidence:** Probe `probe3.py` (`pages/guard.html`, `GUARD_SUBMIT_JS(true)`, then clicking four controls): the form-submit handler ran 0 times and only `b_form_submit` was disabled; the `type=button` `onclick` button and the `div role=button` both ran their handlers. `fill.py:203-217`, `fill.py:553-565`, `tools.py:355`.
- **Impact:** A submission can happen inside the fill stage with no `submit_attempted_at`, no verification and no evidence. The next code step then sees missing fields, raises `fill_failed`, and the run ends `FAILED` (so F2 re-queues it). This silently breaks the documented invariant "no agent ever has a submit tool".
- **Proposed resolution:**
  - Replace the generic `click` and Enter-key `send_keys` in the fix agent with wrappers that refuse the submit candidate. Use one classification function shared with `click_submit`, so the same notion of "Submit" is used to disable and to click, and refuse activation of anything classified as `submit` or `advance`.
  - Disable candidates by that classification instead of by `form` ancestry.
  - Add a post-agent tripwire: after `fix_with_agent`, read signals; if the URL changed or the keyed fields are gone, record `submit_attempted_at` and enter the verification path rather than `fill_failed`.
- **Failure scenario & validating test:** Use `guard.html` as a fixture. Run the wrapped agent tools and assert that `sent_spa`/`sent_div` stay 0; assert that the tripwire fires on a page where the fix agent's click navigated away.

## Documentation discrepancies

- `submit.py` docstring (lines 19-20) and the module wiki claim a re-click happens only on "affirmative evidence the form is still waiting (a code prompt or validation errors)". The code requires only an LLM `needs_fix` verdict, an empty `current_problems()` and a visible CTA (F1).
- `architecture.md` invariant "`submit_attempted_at` ... retries after that only verify" is true for Temporal activity retries only. The API retry route reuses the row and the dedupe paths ignore the marker (F2).
- `agent.md` "fix agent (no submit)" and "No agent ever has a submit tool" hold for our named tools but not for the generic click path (F5).
- `architecture.md` "In flux" section is stale: it lists migration `0017` as untracked and the work as uncommitted; both landed in `999f57a`/`2911263`.

## Proposed action plan

1. Build an offline mock-ATS harness and the submit state-machine tests — outcome: the safety-critical path (`submit_and_verify`, `click_submit`, `fill_form`, executors) is exercised against scripted pages (slow success, silent failure, validation errors, wizard, widget zoo, onClick submit) with a scripted judge, seeded from the scratchpad probes. This is the prerequisite for proving items 2 to 4, and the QA engineer should challenge it independently.
2. Harden the submit boundary (F1, F5, the ordering part of F2) — outcome: structural evidence decides success and re-clicks, a pending state replaces the fixed sleep, the marker is written only once the CTA is located, and agents cannot activate submit candidates.
3. Make uncertainty durable and close the dedupe and retry paths (F2) — outcome: an attempted-but-unconfirmed application is never re-run without a human decision and can be upgraded by an alias-matched confirmation email.
4. Step-aware filling and schema coverage (F3, F4) — outcome: a wizard loop with `advance` versus `submit` classification, broader widget coverage with read-back, and a required-control coverage tripwire; validate on a saved Workday fixture first.
